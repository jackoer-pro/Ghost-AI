## Architecture Decisions

- Generated `components/ui/*` files are never edited after shadcn installation, so they can be regenerated or upgraded safely. One-time exception: the CLI emitted `import { cn } from "cn"` (a third-party npm package), so imports were switched to `@/lib/utils` and the `cn` package removed.
- Dark theme is always on (`dark` class on `<html>`); `globals.css` came with shadcn's light and dark tokens since no dark theme existed beforehand.
- shadcn here uses `@base-ui/react` primitives, not Radix.
- Editor chrome components carry no `"use client"` and hold no state; they take state and handlers as props, so the client boundary sits in whichever parent owns the sidebar state.
- The `New Project` button has no handler yet; it gets wired when the create-project dialog is built.
- `.env.local` only had the Clerk keys, so the standard Clerk vars `NEXT_PUBLIC_CLERK_SIGN_IN_URL=/sign-in` and `NEXT_PUBLIC_CLERK_SIGN_UP_URL=/sign-up` were added; `proxy.ts` falls back to those paths if the vars are missing, so the auth pages can never get locked behind auth.
- `/` does its redirect inside `<Suspense>` because `cacheComponents: true` fails the build on `auth()` read outside Suspense; the Clerk `<SignIn />` / `<SignUp />` components are wrapped the same way.

- Project dialog state lives in one hook (`useProjectDialogs`) using a discriminated union (`closed | create | rename | delete`), so only one dialog can be open and rename/delete always carry their target project. Replacing the mock mutations in `submit()` with API calls is the only change needed when persistence lands.
- Dialog content unmounts the moment `dialog` becomes `closed`, so the 100ms close animation shows an empty popup. Cosmetic; fix by keeping the last dialog around during the exit animation if it bothers anyone.

- `lib/prisma.ts` uses the direct `@prisma/adapter-pg` path only. The spec's Accelerate branch for `prisma+postgres://` URLs is skipped because our `DATABASE_URL` is `postgres://`; add `@prisma/extension-accelerate` and the branch if that ever changes.
- `DATABASE_URL` uses `sslmode=verify-full` (was `require`): pg already treats `require` as `verify-full` today but will weaken it in pg v9, so this pins the current strict behavior.
- Prisma 7 `migrate dev` does not run `generate`; run `npx prisma generate` after each migration.

- `proxy.ts` no longer runs `auth.protect()` on `/api/*`; each API handler calls `auth()` itself and returns JSON `401`/`403`. `auth.protect()` would answer an API call with a redirect or `404`, which breaks the spec's status codes. Every new API handler must do its own auth check.

- Project ID = Liveblocks room ID (decided in feature 07, confirmed by feature 08's `/editor/[roomId]` route). The client builds it as `slug-xxxxxx` and sends it to `POST /api/projects`; the server validates the format and answers `409` on collision. If no `id` is sent the schema's cuid default is used, so feature 06's "no sequential IDs" rule still holds.
- Project mutations refresh server data (`router.refresh()`) instead of patching client state, so the server-loaded lists stay the single source of truth.

- Collaborator emails are stored lowercase (`parseEmail()`), so the `[projectId, email]` unique constraint can't be bypassed by case. Lookups stay case-insensitive.
- API guard convention: `const auth = await authorizeProject(id, "owner" | "member"); if (auth instanceof Response) return auth`. Member access answers `404` for non-members (doesn't reveal the project exists); owner-only answers `403` for collaborators and strangers.

- Known, accepted security trade-offs: (a) spec 09's Clerk enrichment means a project owner can learn whether an email has an account (and its name/avatar) by inviting it; (b) no rate limiting on API routes yet; (c) owner-only routes answer `403` (not `404`) to signed-in strangers, as spec 06 requires, which reveals that a project ID exists. IDs carry a random suffix, which limits (c).
- The project lives in OneDrive, which can turn `.next` build folders into read-only cloud placeholders and make `next build` fail with `EPERM`. Fix: delete the named `.next/...` folder (it's a rebuildable cache). Moving the project to `D:\Projects\` (per the global rules) avoids it.

- Liveblocks auth uses access tokens, not ID tokens: membership is checked in our DB on every token request, so nothing has to be kept in sync with Liveblocks room permissions. Trade-off: removing a collaborator doesn't kick them out of a room they're already connected to; they lose access the next time their token is refreshed. Switch to ID tokens + `usersAccesses` if instant revocation is ever needed.
- The Liveblocks room wraps only the canvas area (`CollaborativeCanvas`), not the navbar or sidebars. Spec 19 also puts presence avatars inside the canvas area, so they fit within this boundary.
- Auth-route 5xx responses (missing secret, Liveblocks `502`) are retried by Liveblocks with backoff and fire no error event, so the canvas shows "Connecting…" until the server recovers. Only 401/403 show the error fallback. Add a `useStatus`-based "still reconnecting" hint if long outages become a problem (see the `handling-unstable-connections` Liveblocks reference).
